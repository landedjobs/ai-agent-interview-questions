# Memory and context engineering

<sub>[Question index](README.md) · [Repo home](../README.md) · Previous: [Planning and reasoning](03-planning-and-reasoning.md) · Next: [MCP](05-mcp.md)</sub>

12 questions, Q36 to Q47. The context window is the agent's only working memory, and everything else is storage you load into it. Interviewers use this section to test whether you treat context as a budget you manage on purpose.

Difficulty is `Core`, `Senior` or `Staff`. `Representative` questions are written by us to match real loops; `Reported` questions link a public source.

<a id="q36"></a>
### Q36. What is context engineering, and how is it different from prompt engineering?

`Core` · `Representative`

**Answer.** Prompt engineering is writing good instructions. Context engineering is deciding everything that goes into the window on each model call: the system prompt, tool definitions, retrieved documents, memory, the message history and tool results, and in what order and size. For a single call they are almost the same thing. For an agent running 50 turns they diverge, because most of the context is generated by the run itself, mostly tool output. Anthropic's post on it describes context as a finite resource with diminishing returns, and calls the degradation as it fills "context rot". So the job is to find the smallest set of high-signal tokens that gets the next step right. The techniques are concrete: just-in-time retrieval instead of preloading, compaction, structured notes kept outside the window, and sub-agents that return summaries instead of raw work.

**Follow-ups**
- *Why not just use a 1M-token window?* Cost and latency scale with it, and models use long contexts unevenly. Lost in the Middle showed accuracy drops for facts placed mid-context.
- *What is the first thing you trim?* Old tool results the agent has already acted on.

**Read:** [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) · [Lost in the Middle](https://arxiv.org/abs/2307.03172)

### Q37. Short-term versus long-term memory in agents: what are they, concretely?

`Core` · `Representative`

**Answer.** Short-term memory is the message history of the current run, the stuff in the window. It is exact and gone when the session ends or gets compacted. Long-term memory is anything persisted across sessions that I can load back in: user preferences, facts learned about the user's systems, past decisions, summaries of earlier tasks. It lives in a database, a vector store, or plain files. Some people split long-term further into semantic memory (facts), episodic memory (past events and runs) and procedural memory (how to do things, like learned instructions or skills). The engineering questions are the same either way: what to write, when, how to retrieve it at the right moment, and how to keep it correct. The model never "remembers" anything on its own. Memory is a read path and a write path that I build.

**Follow-ups**
- *Where does a user's preferred language go?* Long-term profile, loaded into every session's system context.
- *Where does "the user asked to compare two vendors earlier today" go?* Episodic memory, retrieved when relevant.

**Read:** [Generative Agents](https://arxiv.org/abs/2304.03442) · [MemGPT](https://arxiv.org/abs/2310.08560)

### Q38. How do you decide what an agent should write to long-term memory?

`Senior` · `Representative`

**Answer.** Write what will change future behaviour and is likely to stay true. Stated preferences ("always use metric units"), stable facts ("their prod database is Postgres 16"), corrections the user made, and outcomes of past tasks. Do not write transient details or everything the user said; a memory full of noise retrieves noise. I prefer explicit writes, where the agent calls a `remember` tool with a short fact and a reason, over silently embedding every message, because explicit writes are inspectable and testable. I store provenance with each memory: when, from which conversation, and whether the user stated it or the agent inferred it. Users need to see and delete what is stored. And I treat memory as a security surface, because anything written from untrusted content can come back as a trusted-looking instruction in a later session.

**Follow-ups**
- *How do you handle a memory that becomes false?* New facts supersede old ones by key; keep timestamps and prefer the newest; let the user correct it.
- *Inferred versus stated memories?* Lower trust for inferred ones. Confirm before acting on them.

**Read:** [MemGPT](https://arxiv.org/abs/2310.08560)

### Q39. What is compaction, and what goes wrong with it?

`Senior` · `Representative`

**Answer.** Compaction is summarising the conversation when it approaches the context limit, then continuing with the summary plus the most recent turns. It lets a run continue far past one window. Claude Code does this automatically. The risk is losing something that matters, because the summariser decides what is important without knowing what the agent will need later. Typical losses are a constraint the user stated early ("do not touch the billing module"), the exact error message from step 4, or a file path. My mitigations: keep critical state outside the history in files or a state object, not only in turns. Tell the summariser what to always keep: goals, constraints, decisions with reasons, open issues, ids and paths. Clear old tool results first, since they are the bulk and the least needed, before summarising reasoning. And test compaction on long runs by checking whether the agent still obeys early constraints afterwards.

**Follow-ups**
- *Compaction versus truncation?* Truncation drops old turns entirely. It is cheaper and loses more. Fine for chat, risky for agents.
- *When do you trigger it?* At a threshold like 70 to 80% of the window, not at 100%, so the summary call itself fits.

**Read:** [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

<a id="q40"></a>
### Q40. How do sub-agents help with context?

`Senior` · `Representative`

**Answer.** A sub-agent gets a focused task and a clean window, does its work, possibly using tens of thousands of tokens on searching and reading, and returns a condensed result to the parent. The parent's context only grows by the summary. That is context isolation, and it is the main reason I use sub-agents, more than parallelism. A research sub-agent can read 30 pages and hand back two paragraphs with citations. The costs: total tokens go up, the parent loses detail it might have wanted, and the sub-agent lacks the parent's full context, so the task description has to be complete. Anthropic's research system found that vague sub-agent instructions caused duplicated work and gaps, and fixed it by having the lead agent give each sub-agent an objective, output format, tools to use and clear boundaries.

**Follow-ups**
- *When is a sub-agent a bad idea?* When its work is tightly coupled to the parent's decisions, like editing the same files. Cognition argues against splitting for exactly this reason.
- *What should a sub-agent return?* The answer, the evidence, and what it could not find. Not its whole trajectory.

**Read:** [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) · [Don't build multi-agents](https://cognition.ai/blog/dont-build-multi-agents) (Cognition)

### Q41. Just-in-time retrieval or preloading context: which do you choose?

`Senior` · `Representative`

**Answer.** Mostly just-in-time for agents. Instead of stuffing every possibly relevant document into the prompt, I give the agent lightweight references, like file paths, ids or search tools, and let it load what it needs when it needs it. Claude Code works this way: it greps and reads files on demand rather than indexing the repo into the prompt. It keeps the context small and relevant and scales to corpora that would never fit. The cost is latency, since each lookup is a turn, and the risk that the agent does not look. So I preload the small set of things that are always needed, such as a project instructions file, the user profile or the current task spec, and leave the rest to tools. The hybrid is the usual answer. Static, high-value context up front where it caches well; everything else on demand.

**Follow-ups**
- *Agentic search or vector RAG for a codebase?* Grep-style search does very well on code because identifiers are exact. Vector search helps for natural-language questions over docs.
- *How do you make sure the agent looks?* Tell it in the prompt which sources are authoritative, and evaluate on tasks where looking is required.

**Read:** [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

<a id="q42"></a>
### Q42. How does prompt caching change agent architecture?

`Senior` · `Representative`

**Answer.** An agent re-sends a growing history every turn, so most input tokens are repeats. Prompt caching lets the provider reuse the computation for an unchanged prefix, which cuts cost and time to first token a lot on long runs. Both Anthropic and OpenAI document large discounts on cached input tokens. To benefit, I order the context from most stable to least: tool definitions and system prompt first, then long-lived context, then the conversation, and I append rather than edit. Anything that changes the prefix busts the cache: reordering tools, injecting a timestamp at the top, editing an old message during compaction. So compaction and caching pull against each other, and I compact in large steps rather than trimming a little every turn. I track cache hit rate as a production metric, because a regression there shows up as a cost spike with no change in behaviour.

**Follow-ups**
- *Where do you put per-request data like the current date?* After the cached prefix, in the latest user turn.
- *Does caching change outputs?* No. It changes cost and latency only.

**Read:** [Anthropic prompt caching](https://docs.claude.com/en/docs/build-with-claude/prompt-caching) · [OpenAI prompt caching](https://platform.openai.com/docs/guides/prompt-caching)

### Q43. How do you give an agent memory of a codebase or large document set?

`Senior` · `Representative`

**Answer.** Three layers. A small curated file the agent always reads, like a project instructions file with conventions, commands and gotchas; that is the highest-value memory per token. Tools to explore on demand: list, grep, read file ranges, and semantic search over docs if the corpus is prose-heavy. And notes the agent writes as it works, such as a progress file or decisions log, so the next session does not rediscover everything. I avoid embedding the whole repo into the prompt or relying only on vector search for code, because code questions usually hinge on exact names and call paths that grep finds better. For very large document sets I add a proper retrieval pipeline with hybrid search and reranking, and expose it as a tool that returns snippets with sources, not whole documents.

**Follow-ups**
- *Who maintains the instructions file?* Humans, with the agent proposing edits. Unreviewed self-edits drift.
- *How do you keep the index fresh?* Re-index on change events, and have tools read live files for the final answer.

**Read:** [Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices) (Anthropic)

### Q44. Your agent forgets an instruction given 40 turns ago. Why, and what do you do?

`Core` · `Representative`

**Answer.** Likely causes, in order of frequency. It got compacted or truncated away. It is still there but buried mid-context under long tool outputs, where models attend to it less. Or later turns contradicted it, and the model followed the more recent one. I check the transcript to see which. Fixes depend on the cause. Durable instructions belong in the system prompt or a pinned state block re-sent every turn, not only in an old user message. I shrink tool results so the window stays lean. When the user states a lasting constraint mid-conversation, the agent can write it to a constraints list in state, which is then rendered into the context each turn. And for hard rules, I enforce them in tool code, because the cheapest way to make the agent never touch the billing module is to not give it write access to the billing module.

**Follow-ups**
- *How do you test for this?* Long-conversation evals with an early constraint and a later temptation to break it.
- *Repeating the instruction every turn, good or bad?* Fine for a few critical rules if it sits in the cached system prompt.

**Read:** [Lost in the Middle](https://arxiv.org/abs/2307.03172)

<a id="q45"></a>
### Q45. How would you design memory for a personal assistant agent used daily?

`Staff` · `Representative`

**Answer.** I would separate memory by type and trust. A profile store with explicit preferences and facts, small enough to load every session, editable by the user. An episodic store of past conversations and task outcomes, summarised at session end and retrieved by relevance and recency when a new request looks related. Procedural memory as short learned instructions, like "when booking travel for this user, prefer aisle seats", kept small and reviewed. Writes happen through an explicit tool or an end-of-session reflection step, with provenance. Reads happen at session start for the profile, and on demand for episodic memory through a search tool. Then the hard parts. Conflicts get resolved by recency and source. Privacy needs per-user isolation, user-visible memory, and deletion that actually deletes, including from vector indexes. And security: content from emails or web pages must never write memories without a gate, or one injected email becomes a permanent instruction.

**Follow-ups**
- *How do you evaluate memory?* Multi-session test scripts: tell a fact in session 1, check it is used correctly in session 3 and forgotten after deletion.
- *How big does the profile get before it hurts?* Keep it to a few hundred tokens and summarise. A sprawling profile crowds out the task.

**Read:** [MemGPT](https://arxiv.org/abs/2310.08560) · [Generative Agents](https://arxiv.org/abs/2304.03442)

### Q46. What is "context rot" and how do you measure it in your own agent?

`Senior` · `Representative`

**Answer.** It is the drop in a model's ability to use information correctly as the context grows. Anthropic's context engineering post uses the term and ties it to how attention spreads over more tokens. It is not a cliff at the window limit, it is a gradual decline, and it varies by model and task. I measure it on my agent directly rather than trusting a general benchmark. I take tasks the agent solves with a short context, then pad the context with realistic filler, like old tool outputs from other tasks, at increasing lengths, and plot success rate against context length. I also plant a needed fact at different depths. That curve tells me where to set the compaction threshold and how aggressively to trim tool results. It usually argues for a smaller working context than the advertised window.

**Follow-ups**
- *Is needle-in-a-haystack enough?* No. Finding one planted string is easier than reasoning over many relevant pieces spread through the window.
- *Does a bigger window fix it?* It moves the limit; it does not remove the decline.

**Read:** [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### Q47. Where should agent state live: the conversation, a database, or files?

`Senior` · `Representative`

**Answer.** The conversation is a view, not a store. I keep authoritative state in a database or files and render the parts the model needs into the context each turn. Run state, like the current step, the plan, completed items, pending approvals and budgets spent, lives in a durable store keyed by run id, so a crashed worker can resume and a UI can show progress. Artifacts the agent produces, like code, reports or datasets, live in files or object storage, and the context holds paths and summaries. User-level memory lives in its own store with access control. This split is what makes agents restartable, auditable and testable, because I can replay a run from stored state. The conversation history is still saved for traces and debugging, but nothing important exists only there.

**Follow-ups**
- *What breaks if state only lives in the conversation?* Restarts, compaction, concurrent workers, and any audit question about why something happened.
- *How does a workflow engine help?* It persists each step's inputs and outputs for you and replays on failure.

**Read:** [Temporal workflows](https://docs.temporal.io/workflows) · [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
